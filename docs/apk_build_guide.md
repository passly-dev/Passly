# Android APK ビルド & イベント配布・運用ガイド 📱

本ドキュメントは、Passly（BLEすれ違い通信アプリ）のAndroid APKを作成し、イベント会場でテスト利用・配布を行うための設計仕様、ビルド手順、およびチーム開発における運用上の注意点をまとめたものです。

---

## 1. APK の設計方針と概要

### 1.1. APK（Android Application Package）とは
Android OS上でアプリを直接インストール・実行するためのパッケージ形式です。
Google Playストアを通さないイベント会場での実機テストや、関係者への先行配布（サイドローディング）にはAPK形式を用います。

### 1.2. ビルド種別（Build Types）の選定
本プロジェクトでは、イベント用途に応じて以下の2つのビルドを使い分けます。

| ビルド種別 | 目的・用途 | 特徴・選定理由 |
|---|---|---|
| **Release ビルド**<br>`--release` | **イベント配布・実機テスト（推奨）** | コード最適化・軽量化が行われており、BLEスキャンのバックグラウンド継続動作やバッテリー消費が本番同様に動作します。 |
| **Debug ビルド**<br>`--debug` | 開発中の動作確認・ログ調査 | デバッグログが詳細に出力されますが、Flutterエンジンのオーバーヘッドがあり、パフォーマンス評価には不向きです。 |

### 1.3. モード種別の選定（通常版 vs デモ版）
PasslyにはバックエンドAPIと通信する**「通常版」**と、サーバー不要で動作する**「デモ版」**の2つのモードがあります。

| モード | フラグ | 想定シナリオ | 特徴 |
|---|---|---|---|
| **通常版** | (なし) | サーバーが稼働している本番テスト環境 | 実際にBLEでトークンを交換し、サーバーとすれ違い履歴を同期します。 |
| **デモ版** | `--dart-define=DEMO_MODE=true` | サーバー未接続・オフラインの展示・体験会 | サーバーログイン不要でダミーデータですぐにUI操作が可能です（※BLEすれ違いは動作しません）。 |

## 2. ビルド手順（再現性と安全性の確保）

チーム開発環境において、外部パッケージの予期せぬアップデートや環境差異によるビルド破壊を防ぐため、**`--no-pub` オプションを付与して既存の依存関係を厳格に保持したビルド**を行います。

### 2.1. 自動ビルドスクリプトの利用（推奨）

リポジトリルートにて以下のスクリプトを実行します。

```bash
# 通常版とデモ版のRelease APKを両方ビルド（イベント準備時）
./scripts/build_apk.sh --all

# デモ版のRelease APKのみビルド
./scripts/build_apk.sh --demo

# 通常版のRelease APKのみビルド
./scripts/build_apk.sh --release
```

成果物は `build/outputs/apk/` に日付スタンプ付きで出力され、同一ディレクトリに `passly-*-latest.apk` および改ざん検証用の `passly-*-latest.apk.sha256` が生成されます。

### 2.2. 手動でのFlutterビルドコマンド

スクリプトを使わず手動でビルドする場合は、以下のコマンドを実行します。

```bash
# 通常版 Release APK
flutter build apk --release --no-pub

# デモ版 Release APK
flutter build apk --release --no-pub --dart-define=DEMO_MODE=true
```
※ ビルドされたAPKは `build/app/outputs/flutter-apk/app-release.apk` に生成されます。

### 2.3. GitHub Actions による自動ビルド＆リリース（推奨）

ローカル環境の差異や作業負担をなくすため、GitHub Actions ワークフロー（`.github/workflows/release_apk.yml`）を用意しています。タグの push または GitHub の Web 画面から実行することで、クラウド上で通常版・デモ版の APK が自動ビルドされ、GitHub Releases に即座に公開されます。

#### A. バージョンタグを push して自動公開する場合
```bash
# バージョンタグを作成（例: v1.0.0-event）
git tag v1.0.0-event

# タグをリモートに push（これだけでビルドとReleases作成が自動実行されます）
git push origin v1.0.0-event
```

#### B. GitHub の Web 画面から手動で実行する場合
1. GitHub のリポジトリページを開き、**「Actions」** タブを選択します。
2. 左側のワークフロー一覧から **「Build and Release Android APK」** を選択します。
3. **「Run workflow」** ドロップダウンをクリックし、タグ名（例: `v1.0.0-event`）を入力して実行ボタンを押します。
4. 数分でビルドが完了し、Releases ページに `Passly-Production.apk` および `Passly-Demo.apk` が添付されたリリースが公開されます。

## 3. 実機へのインストール手順

### 方法A: USBデバッグ接続（adb経由・開発者向け）

PCとAndroid端末をUSBケーブルで接続し、端末側で「USBデバッグ」を許可した状態で実行します。

```bash
# APKを直接端末にインストール
adb install -r build/outputs/apk/passly-production-release-latest.apk
```
※ `-r` オプションは既存アプリのデータ（設定等）を保持したまま再インストールする指定です。

### 方法B: ファイル共有（Google Drive / AirDrop / Slack等）

1. 生成された `.apk` ファイルをテスターやイベント参加者のAndroid端末に送付します。
2. Android端末の「ファイル」アプリ等でAPKを開きます。
3. 「提供元不明のアプリのインストール」を許可し、画面の指示に従ってインストールを完了します。

## 4. グループ開発における影響・注意点

### 4.1. デバッグ署名（debug.keystore）の競合問題
* **現象**: 開発者AのPCでビルドしたAPKがすでに端末に入っている場合、開発者BのPCでビルドしたAPKを上書きインストールしようとすると「署名が競合しているためインストールできません」とエラーになります。
* **原因**: PCごとにローカルのデバッグ用証明書（`debug.keystore`）が異なるためです。
* **対処**:
  1. 端末側の既存アプリを一度アンインストールしてから、新しいAPKをインストールしてください。
  2. ※アンインストールすると端末内に保存されていたすれ違い履歴やオフラインデータは消去されますのでご注意ください。

### 4.2. Androidメーカー固有の省電力・タスクキル対策
PasslyはBLEの常時スキャン・アドバタイズを行うため、端末メーカー（特にXiaomi, AQUOS, Galaxy等）の強力なバッテリー最適化機能によってバックグラウンド動作が停止される場合があります。
* **テスト時の推奨設定**:
  1. 端末の「設定」>「アプリ」>「Passly」を開く。
  2. 「バッテリー」設定を「最適化」から**「制限なし」**に変更する。
  3. Bluetoothおよび位置情報の権限が「常に許可」または「アプリ使用中のみ許可」になっていることを確認する。

### 4.3. 時間管理ルールの遵守
`README.md` に記載の通り、アプリ内の時間管理には以下の絶対ルールがあります。
1. **UI表示・日またぎ判定**: 必ず `AppTime` (JST固定) を使用。
2. **システム保存・API通信**: 必ず `DateTime.now().toUtc()` を使用。
イベントテスト時、端末の時計を手動で変更した場合でも、バックエンドとの不整合が発生しないよう上記仕様が守られていることを確認してください。
