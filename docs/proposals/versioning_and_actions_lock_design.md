# GitHub Actions によるバージョン管理方針 & `gh actions-lock` 導入設計提案書 🚀

本ドキュメントは、Passlyプロジェクトにおける**「自動ビルドと連動したバージョン管理（バージョニング）の手法」**、および**「`gh actions-lock` を活用した CI/CD サプライチェーンセキュリティ強化方針」**について、チーム開発の観点から整理した設計提案書です。

---

## 1. 自動ビルドにおけるバージョン管理（バージョニング）の設計手法

### 1.1. 現状の課題
Flutter アプリには以下の2つのバージョン情報が存在します：
* **`versionName`（表示バージョン）**: ユーザーに見えるバージョン（例: `1.0.0`）。
* **`versionCode`（ビルド番号）**: OSやストアが更新判定に使う整数（例: `1`）。

現状では `pubspec.yaml` に `version: 1.0.0+1` とハードコードされており、手動運用では「Git タグ」「GitHub Releases」「アプリ内のバージョン情報」の間で不整合が発生するリスクがあります。

---

### 1.2. バージョン管理手法の比較と選択肢

| 手法 | 概要 | メリット | デメリット・チーム開発への影響 |
|---|---|---|---|
| **案A: Git Tag 駆動型<br>（現フェーズ推奨）** | `git tag v1.1.0` を push すると、CI がタグ名からバージョンを抽出し、`flutter build apk --build-name=1.1.0 --build-number=${{ github.run_number }}` を実行してビルド。 | ・直感的でミスが少ない<br>・コード変更コミットなしでバージョン発行可能<br>・ビルド番号が CI の実行番号と自動同期 | ・タグを打つ運用ルールをチームで統一する必要がある |
| **案B: Release Please 連携型<br>（将来推奨）** | コミットメッセージ（Conventional Commits: `feat:`, `fix:` 等）を解析し、Google 製の `release-please` が自動で CHANGELOG 生成＆Release PR を起票。マージ時にタグ・リリース発行。 | ・完全自動化<br>・CHANGELOG が漏れなく作成される<br>・セマンティックバージョニング（SemVer）の強制 | ・コミットメッセージ規約の徹底が全員に求められる |
| **案C: `pubspec.yaml` ソースオブトゥルース型** | PR で `pubspec.yaml` の数値を更新し、main マージ時に CI がタグを打つ。 | ・開発者がコード上でバージョンを把握しやすい | ・毎回ファイルを書き換えて PR を出す手間が発生する |

#### 【提案】段階的導入プラン
1. **フェーズ1（現状〜イベント本番）**: **案A（Git Tag 駆動型）**
   * タグ `vX.Y.Z` を push するだけで、Flutter ビルド時に `--build-name` と `--build-number` を動的に注入し、リリースページとアプリ内バージョンを完全一致させます。
2. **フェーズ2（本番リリース後）**: **案B（Release Please）**
   * チームが拡大した段階で、PR のコミット規約と連動した自動リリースへ移行します。

## 2. `gh actions-lock` による CI/CD サプライチェーンセキュリティの強化

### 2.1. 背景：GitHub Actions におけるサプライチェーンリスク
昨今、CI/CD パイプラインを標的としたサプライチェーン攻撃が増加しています。
GitHub Actions のワークフローで一般的なタグ指定（例: `uses: actions/checkout@v4`）を行っている場合、**3rd party アクションのタグが攻撃者によって改ざん・上書きされた際に悪意あるスクリプトが混入するリスク**があります。

これを防ぐためコミット SHA によるピン留め（例: `uses: actions/checkout@3d3c4...`）が推奨されてきましたが、従来の SHA 指定には以下の問題がありました：
1. **可読性の悪化**: どのバージョンを使っているかが一目でわからない。
2. **Dependabot の制限**: コミット SHA 指定では Dependabot のセキュリティアラートが機能しない。
3. **推移的依存の未保護**: 指定した Action が内部で別の Action を呼んでいる場合、そこまでは保護できない。

---

### 2.2. 公式拡張機能 `gh actions-lock` の特徴
2026年より GitHub 公式から提供されている `gh actions-lock` は、npm の `package-lock.json` や Flutter の `pubspec.lock` と同様に、**Actions のロックファイル（`.github/workflows/actions.lock`）を生成・管理する仕組み**です。

```
リポジトリ
├── .github/
│   └── workflows/
│       ├── release_apk.yml    # 可読性の高いバージョン表記のまま維持
│       └── actions.lock       # すべての推移的依存を含めたコミットSHAを厳格に記録
```

* **メリット**:
  * ワークフローの見た目は `@v4` や `@v2` のままで可読性を維持。
  * `actions.lock` がすべての依存関係をコミット SHA で再帰的に固定。
  * **Dependabot が公式対応済み**であり、セキュリティアップデートの PR が自動で送られ、同時に `actions.lock` も自動更新される。

---

### 2.3. Passly における具体的な導入設計

#### ステップ 1: CLI によるロックファイルの生成
開発者が以下のコマンドを実行し、ロックファイルを生成してリポジトリにコミットします。
```bash
# GitHub CLI 拡張機能のインストール
gh extension install github/gh-actions-lock

# ロックファイルの自動生成
gh actions-lock
```

生成される `actions.lock` の例：
```yaml
# This file is machine-generated by `gh actions-lock`.
version: 'v0.0.2'
workflows:
    '.github/workflows/release_apk.yml':
        - 'actions/checkout@v4'
        - 'actions/setup-java@v4'
        - 'subosito/flutter-action@v2'
        - 'softprops/action-gh-release@v2'
dependencies:
    'actions/checkout@v4':
        ref: 'v4.2.2'
        commit: 'sha1-11bd71901bbe5b1630ceea73d27597364c9af683'
    # ... すべての依存が SHA ピン留めされる
```

#### ステップ 2: CI による非ピン留め Action の検知（ガードレール）
PR 作成時の CI ワークフローに以下のチェックを追加することで、未検証の 3rd party Action が紛れ込むのを未然に防ぎます。
```bash
# ロックファイルとワークフローの整合性を検証（不整合なら exit 1）
gh actions-lock --no-fix
```

#### ステップ 3: Dependabot の設定
`.github/dependabot.yml` を配置し、Actions のバージョン更新を自動追従します。
```yaml
version: 2
updates:
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"
```

## 3. まとめとチームへの提案

1. **バージョン管理**:
   * 直近のイベント配布・検証では **Git Tag 駆動型（案A）** を標準とし、タグ名から動的にアプリ内バージョンを注入する構成を採用する。
2. **Actions セキュリティ**:
   * CI/CD の堅牢化として、先行して **`gh actions-lock`** を導入し、チーム開発における「安全な自動ビルド基盤」を確立する。
